# ADR 0001: Native Rust CDP client for browser credential filling

Status: accepted, 2026-09-24. Closes Phase A of `../credential-fill.md`.

## Context

The credential filling design needs a Chrome DevTools Protocol (CDP)
transport that attaches to an existing Chromium-family browser, targets one
page, frame chain, and element, and replaces the element's content with a
credential value. Two implementations were possible: a native Rust CDP client
inside the `agentenv` binary, or a Node.js helper using `playwright-core`
`chromium.connectOverCDP()`. The design allowed the native client only if it
reached full parity with the Playwright reference on every item of the filling
contract; a partial native implementation was not an option.

## Decision

Implement the CDP backend as a native Rust client. The Node.js helper is not
needed for CDP. It remains the transport for the later Playwright
shared-endpoint milestone only.

## Evidence

The lab in `tests/cdp_lab/` ran both implementations through 45 scenarios
against the same fixture pages in one browser, with a separate Playwright
host session opening the pages and verifying afterwards that it could still
drive them. Receipts posted by the fixture pages, not client readback,
established the delivered value and the trusted event sequence.

Timing over the 16 filled scenarios: native median 14 ms per operation
(one first-run outlier of 1.0 s), reference median 212 ms. Error paths:
native median 8 ms, reference 189 ms. The native client spawns no process
and loads no runtime.

### Protocol surface of the native client

HTTP `GET /json/version` for the WebSocket URL; `Browser.getVersion`;
`Target.getBrowserContexts`, `Target.getTargets`, `Target.attachToTarget`
(flatten), `Target.setAutoAttach` (flatten, no debugger wait) on every owned
session, `Target.detachFromTarget`, and the `Target.attachedToTarget` and
`Target.detachedFromTarget` events; `Emulation.setFocusEmulationEnabled`
(as Playwright does, so focus events fire in an unfocused window);
`Page.getFrameTree`; `Page.createIsolatedWorld` (one owned world per frame,
reused for revalidation so element identity can be compared);
`Runtime.callFunctionOn` with fixed scripts only; `DOM.describeNode` to map
an iframe element to its frame id; `Input.insertText` on the page session,
which the browser routes to the focused frame including out-of-process
frames. No target, context, or page is created or closed.

### Contract narrowings relative to Playwright `fill`

Both clients apply these deliberately; they are part of the filling contract,
not parity gaps:

- A selector must name the control itself. Playwright would retarget a
  `<label>` to its control; the contract rejects it as unfillable.
- Date, time, color, range, and similar inputs are unfillable. Playwright
  would set their value directly.
- Open shadow roots are pierced per root for the whole selector. Playwright's
  engine also matches compound selectors across shadow boundaries; the lab
  did not exercise that and the contract does not promise it.
- Role computation covers form controls and contenteditable elements, which
  is the set the contract accepts.

## Recording detection

A second CDP client cannot observe Chromium tracing, screencast, screen
recording, screenshots, Playwright tracing, or Playwright HAR started by
another client without starting a recorder itself; Playwright video uses
screencast and was not exercised because its ffmpeg companion was absent. An
open DevTools window is observable through `Target.getDevToolsTarget` and
`devtools://` targets, but the Recorder panel's state is not. Full findings:
`tests/cdp_lab/recording_probe/` and the consumed research result for
attempt `recording-2`.

## Consequences

- Phase C implements the CDP backend in Rust inside the main binary, moving
  the prototype's protocol handling onto the existing tokio runtime and the
  design's deadline and resolver stages. The protocol surface above is the
  implementation scope.
- The first browser release has no Node.js runtime dependency, no helper
  asset bundle, and no helper protocol version to check.
- Preflight treats an open DevTools window on the target page as a
  detectable conflict; every other recorder is a documented host
  prerequisite, and the fill result must not claim their absence.
- The Playwright milestone (Phase G) still needs the Node helper and its
  packaging; nothing here changes that scope.

## Residual risks and unverified areas

- Only Microsoft Edge 153 in headless mode was tested; no Chrome or Chromium
  build is installed on the lab machine. Chrome and Chromium 136 and later
  require a non-default `--user-data-dir` for remote debugging.
- The prototype is synchronous; production integration into the tokio
  runtime is implementation work, not a protocol question.
- `Input.insertText` for out-of-process frames was proven on the page
  session; the routing is browser behavior, so the Phase C tests keep the
  cross-origin scenarios.
- The one-second first-run outlier was not diagnosed; every later native
  operation completed in under 20 ms.
